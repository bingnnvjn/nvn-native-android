# 架构

> 这是一个新项目，不是现有项目的拼装。
> 接口、骨架、模块边界由我们自己定；现有项目是**依赖、参考实现与零件库**，不是基座。
> 细节上可以复用代码、移植逻辑、借鉴思路，但大局是我们自己的架构。

## 1. 完全体由两半拼成

```
APK（CI 编译，无游戏数据，可公开）
        +
import pack（本机用你的 ROM 生成，不可公开）
        =
        可在手机上玩
```

- **APK**：我们的程序。平台壳、host、图形引擎、着色器缓存读取器都在里面。
- **import pack**：从你自己的 XCI/NSP 解出的游戏代码、RomFS 资源、着色器表。
- **keys**：只在电脑上生成 import pack 时用一次，**不上手机、不进仓库**。
- **游戏本体代码**：属于 import pack，不属于 APK。我们不改写它的授权，只在本机改写它的指令。

## 2. 运行时：一帧是怎么出来的

```
┌──────────────────────────┐
│ BotW 原版代码（ARM64）    │
│ 经重写器改写后的那份      │
└───┬──────────────────┬───┘
    │ 系统调用（SVC）    │ NVN 绘图
┌───▼─────────┐   ┌────▼──────────┐
│ host        │   │ 图形引擎       │
│ 系统服务替身 │   │ NVN → Vulkan   │
└───┬─────────┘   └────┬──────────┘
    │ 文件/音频/手柄     │ Vulkan
┌───▼──────────────────▼──────────┐
│ 平台壳 + Android                 │
│ 窗口 / 音频 / 输入 / 驱动         │
└─────────────────────────────────┘
```

游戏代码在中间：向左要系统服务，向右要画面。左右两边都由我们实现。

## 3. 七层

| 层 | 作用 | 做法 | 语言 |
|---|---|---|---|
| L1 平台壳 | 提供窗口、Vulkan 表面、输入、音频输出、生命周期、导入 pack | GameActivity + Vulkan WSI + AAudio + SAF；JNI 进引擎 | Kotlin + Rust |
| L2 加载器 | 读 import pack，映射内存，应用重写结果，跳入口 | 解析 NSO/NRO、`mmap`、设 TLS、调用 `main` | Rust |
| L3 重写器 | 改掉安卓不认的指令（SVC、线程指针、栈对齐） | ARM64 解码 → 定位 → 替换 → 分支重定位 | Rust（构建期） |
| L4 host / HLE | 替游戏应答系统服务：线程、同步、内存、文件、音频、手柄、时间 | SVC 陷入转发到 C 函数；服务用 Android API 实现 | C/C++ 起步，逐步迁 Rust |
| L5 图形引擎 | 接住 `nvn*`，翻译成 Vulkan：命令、状态、纹理、同步、上屏 | 命令记录/重放、状态哈希→pipeline、去 swizzle、fence/present | Rust + `ash` |
| L6 着色器 | Maxwell 指令 → SPIR-V；按变体预编译 | 构建期用 Ryujinx 翻译器批量翻译，运行时只查表 | 构建期 .NET + 自研缓存（Rust） |
| L7 驱动/硬件 | 真正执行 | Adreno 驱动或 Turnip | 第三方 |

## 4. 构建时：从 ROM 到能玩

```
XCI / NSP + prod.keys
        │ nstool 解包
        ▼
  ExeFS（main 等）+ RomFS
        │ 重写器：按 build ID 打补丁
        ▼
  改好的模块 + 资源
        │ 着色器预编译（.NET 工具）
        ▼
   import pack ──┐
                 ├── 手机 ──► 可玩
   APK（CI）─────┘
```

APK 的编译不需要游戏数据：它只含代码与资源；游戏数据由 import pack 在设备上导入。

## 5. 语言与占比

**这是估算区间，不是承诺。** 占比指“我们自己写的源码行数”，不是 APK 体积。

| 语言 | 用在哪 | 源码占比（估算） | 说明 |
|---|---|---|---|
| **Rust** | 图形引擎、加载器、重写器、验证工具、部分平台胶水 | **55–65%** | 新代码的主力；随 host 迁移而上升 |
| **C / C++** | host 的起步实现、第三方库（lz4、mbedtls、libdeflate、Turnip 加载器） | **25–35%** | 起步时更高，逐子系统迁移后下降 |
| **Kotlin** | 安卓壳：Activity、权限、SAF、前台服务、UI | **5–10%** | 行数少，但没它就没有窗口 |
| **ARM64 汇编** | SVC 蹦床、少量 ABI 垫片 | **< 2%** | 只在边界出现 |
| ~~GLSL~~ | 不写 | 0 | 着色器由游戏提供，我们只翻译 |

**不进 APK 的语言**：

- **Python**：构建与验证脚本（不随 APK 分发）。
- **C#**：着色器翻译器（构建期工具，进程隔离）。
- **ObjC/Swift**：只在 macOS/iOS 上游项目里，与我们无关。

**为什么 Rust 占大头**：引擎的资源生命周期、命令编码、并发状态最吃内存安全；工具链也全在 Rust。**为什么 C/C++ 不能立刻消失**：host 的语义最密，现有 C 实现是唯一参照，先保正确性，再用等价性测试逐块换。

## 6. 一帧的生命周期

1. 游戏算完逻辑，调 `nvnCommandBuffer...` 记录“要画什么”。
2. 引擎把记录翻译成 `vkCmd*` 并提交。
3. GPU 执行，交换到屏幕。
4. 同时 host 在别的线程处理音频、输入与文件。

## 7. 谁负责什么（边界）

- **host ⇄ 引擎**：只通过 C ABI 的窄接口；内存归属与 GPU 地址翻译必须在接口上写清。
- **引擎 ⇄ 壳**：壳只提供 `VkSurface`、输入事件、音频回调，不碰引擎内部。
- **Rust ⇄ C**：`extern "C"`；Rust 侧 `panic=abort`，不允许 unwind 穿过边界。
